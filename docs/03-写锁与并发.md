# 03 · 写锁与并发

## 场景

两个 AI 工具（或一个人 + 一个 AI）同时改同一台服务器：

- A 在改 `index.html`，B 也在改；
- A 先传，B 后传，A 的改动被静默覆盖；
- 没有报错，没有日志，第二天才发现页面回退了。

## 为什么不用「人工协调」

「我改的时候你说一声」在两个人之间勉强能用，在多个 Agent 之间完全不成立：
Agent 不会记得在群里说一声，也不会等你回复。

**能落盘的协调，才是协调。**

## 做法：一个 JSON 锁

`.agent-coordination/server-lock.json`：

```json
{
  "lock_holder": "cli-agent",
  "operation": "发布登录页",
  "started_at": "2026-10-19T09:20+08",
  "expected_done": "2026-10-19T09:50+08",
  "last_done": {
    "at": "2026-10-19T09:44+08",
    "task": "发布登录页",
    "result": "退出码 0，页面可访问"
  }
}
```

三步：

```bash
bash scripts/lock.sh acquire "发布登录页" 30   # ① 拿锁
bash scripts/deploy.sh web/index.html          # ② 执行
bash scripts/lock.sh release "退出码 0"        # ③ 释放
```

`deploy.sh` 会先检查锁：没锁就拒绝发布（除非显式 `--force`）。

## 三条规则

1. **锁超时自动失效**：`expected_done` 过了，别人可以接管，不靠人记得释放。
   （实现上可在 `lock.sh` 里加判断；本脚手架留了字段，按需启用。）
2. **重跑必须幂等**：同一条命令跑两次，结果必须一致。否则回滚和重试都会制造新问题。
3. **冲突就等，不硬闯**：锁在别人手上时，先做不冲突的部分，或者去推进别的卡。

## 锁不是权限

锁不阻止任何人，它只回答一个问题：**现在有没有人在动。**

真正阻止破坏性操作的是 `AGENTS.md` 里的红线：删库、改权限、动生产数据，必须人工拍板。

## 一句话

> 并发的解法不是排队等人，是把状态写进文件。
