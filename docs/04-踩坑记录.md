# 04 · 踩坑记录

> 每条都真实发生过。写下来不是卖惨，是让下一次少花半天。

## 1. UTF-8 BOM 把整条协作链弄坏

**现象**：`tasks.json` 看起来完全正常，脚本一读就报 `Expecting value: line 1 column 1`。

**原因**：Windows PowerShell 的 `Set-Content` 默认带 BOM，JSON 前面多了三个不可见字节。

**处理**：

- 所有读取都用 `encoding="utf-8-sig"`（本仓库的 `taskboard.py` 已这样处理）。
- 写文件时显式 `-Encoding UTF8`，或者干脆用 Python 写。
- 在 `newtask.sh` 里加一道校验：**JSON 不合法就中止，绝不覆盖**。

## 2. 沙箱里「写成功」了，磁盘上什么都没有

**现象**：命令返回 0，日志显示写入完成，但文件不存在。

**原因**：某些 Agent 的沙箱会把写入重定向到临时层，进程结束就丢。

**处理**：写完立刻 `ls -l` / `cat` 回读一次；不放心就用 `python -c "open(...).read()"`。
本仓库所有生成类脚本都会在最后打印产物路径，便于回读确认。

## 3. 时区差 8 小时

**现象**：日报在「早上 9 点」发，实际每天 17 点才到。

**原因**：服务器是 UTC，人看的是北京时间，cron 按 UTC 解释。

**处理**：

- 定时任务统一写成显式时区（systemd 用 `Timezone=`，或脚本里 `TZ=Asia/Shanghai`）。
- 时间戳一律带偏移（本仓库用 `%Y-%m-%dT%H:%M`，并在文档里注明时区）。

## 4. 手改 JSON 出现重复 key，锁直接失效

**现象**：`server-lock.json` 里出现两个 `lock_holder`，解析后取到 null，锁形同虚设。

**原因**：多人（或多个 AI）同时手改同一个 JSON。

**处理**：

- 锁只允许通过 `lock.sh` 改，禁止手改。
- 写入用「临时文件 + 原子替换」，避免写一半被打断。
- 需要并发时，先拿锁再改锁文件（听起来绕，但这是唯一稳的顺序）。

## 5. 静默失败 17 天没人发现

**现象**：仓库监听脚本因为路径被改写，一直没有触发；17 天后才被发现。

**原因**：失败只写进了日志，没有通知任何人。

**处理**：

- 任何后台任务失败必须**主动通知**（`NOTIFY_CMD`）。
- 巡检要记轮次（`patrol.sh` 的 `round`），**没有轮次增长的「正常」是假正常**。
- 判断「有没有在跑」，看轮次，不看最后一条日志的时间。

## 6. 定时任务挂在个人电脑上

**现象**：连续 4 天没收到日报，程序、登录、定时任务全都「看起来正常」。

**原因**：任务挂在个人电脑的 cron 上，人不开机就没有任务。巡检记录里出现的 26 小时空档是唯一线索。

**处理**：定时任务放到服务器（systemd timer / cron），不要依赖某一台个人设备开机。

---

## 一条通用经验

> 失败不可怕。可怕的是失败**没有留下可读的原因**，于是只能重开一轮。

所以本仓库坚持三件事：**命令、输出、时间戳**。
